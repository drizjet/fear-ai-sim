## 1. Purpose & Operating Principles

This ledger establishes the **single authoritative status record** for every live capability across the Fear AI middleware system. It supersedes all legacy checklists (including `PROJECT_STATUS.md` and historical evidence JSON dumps) and enforces four core operating principles:

1. **Host Game Authority Invariant**: Fear AI is strictly non-mutating intelligence middleware. The host game engine retains 100% exclusive authority over transforms, movement, physics, pathfinding, combat, damage, spawning, and inventory. Fear AI emits non-binding advisory intent vectors and affective state signals only.
2. **Zero Fabrication & Parity Standard**: A feature is not complete because a file exists, a test passed historically, or an audit counted it. A capability is certified only when its contracts, live callers, consumers, persistence lifecycle, authority boundaries, and known failure modes are mathematically verified.
3. **Modular Release Tiering**:
   - **Tier 1: Core Affective SDK**: The foundational deterministic runtime (`FearCore`, `AffectiveAgent`, `RuntimeSimulation`, `BinaryWireProtocol`, `HostCapabilityNegotiator`).
   - **Tier 2: Optional Modular Extensions**: Standalone plug-in systems for tactical coordination, social rumors, and macroeconomics (`PackCoordinationEngine`, `EpistemicBeliefEngine`, `EconomicFeedbackSystem`, `SettlementMigrationSystem`).
   - **Tier 3: Tooling & Analytics**: Visual inspection, replay, and causal analytics (`DesignerDashboardServer`, `WorldCounterfactualEngine`).
   - **Tier 4: Engine Adapters**: Host engine bridges (`Godot 4.6`, `Unity UPM`, `Unreal Engine 5`).
   - **Tier 5: Research & Experimental**: Unfinished research frontiers (`FABE Functional Persona Signatures`, `MoralDissonanceEngine`).
4. **Controlled Status Taxonomy**:
   - `VERIFIED_CURRENT`: Implemented for the explicitly documented scope, traced to its current callers and consumers, and supported by a standalone deterministic proof artifact. This label does not imply universal integration, external adoption, or proof beyond the named scenarios.
   - `SCENARIO_VERIFIED`: A standalone CLI, reference-world, or optional module path is implemented and supported by a deterministic proof, but it is not an automatic `RuntimeSimulation` service or a general external-host integration claim.
   - `PARTIAL`: Code exists and runs, but has known missing persistence, incomplete editor verification, or unverified wiring.
   - `PARTIAL (UNREPRODUCIBLE_RECORDED_HOST_EVIDENCE)`: Named historical host evidence exists, but a clean rebuild from its recorded commit failed or depended on source outside that commit; no current host certification is implied. Retained as a defined status but no longer applied to the Pixel Pets row.
   - `VERIFIED_CURRENT (HOST_DIAGNOSTIC_CLEAN_COMMIT)`: A host-integration row whose committed diagnostic builds and passes from a clean checkout of a single named host commit. Bounded to that diagnostic's scope; it does not imply universal engine, host-game, or multi-engine certification.
   - `VERIFIED_CURRENT (STATION_ADVISORY_CONTRACT)`: A showcase/host-visual row whose per-station advisory behavior is independently asserted by a standalone source-and-core probe. Bounded to the advisory contract (station inventory, wiring coverage, direction, ordering, thresholds, fail-safety, and the advisory-only boundary); it is not a live in-engine run, not a rendering/visual-fidelity claim, and not an engine certification.
   - `EXPERIMENTAL`: Code exists as a prototype or research model, but lacks a live host consumer or has unresolved stability/entanglement challenges.
   - `BLOCKED`: Development or certification is blocked on external resources (e.g. human participant evaluations).
   - `DEFERRED`: Intentionally postponed by owner policy decision (e.g. Unreal Engine 5).
   - `HISTORICAL`: Preserved legacy research or early browser simulation capability.
5. **RC1 Release Surface (`docs/RELEASE_SURFACE.md`)**: The release candidate is the **in-scope middleware contract** only — the core affective SDK, intent/host negotiation, protocol, runtime transport, engine adapters, and the designer tooling. **Tier 2 optional modules, Tier 3 analytics beyond the dashboard, the standalone world-sim/research tail, the Elixir tree, and the deferred Unreal adapter are out of scope**: they ship as separate standalone tools or remain research, and no release claim may depend on them being automatic `RuntimeSimulation` services. `tools/verification/verify_runtime_wiring.mjs` (code boundary) and `tools/verification/verify_release_claim_boundaries.mjs` (document boundary) enforce this; a module joins the release surface only via the change policy in `docs/RELEASE_SURFACE.md`.

### 18. Batch Agent Registration (`POST /api/v1/register/batch`, `MESSAGE_TYPES.REGISTER_AGENT_BATCH`) — server + binary wire + Godot client
- **Why it exists**: the control plane carries one HTTP request at a time and deliberately keeps registration serialized ahead of the data plane, so registering N agents cost N round trips and a large host spent seconds of dead time before its first advisory. Because an unregistered agent reads to a host as "the middleware returned nothing", that cost is also a correctness hazard near session start.
- **Endpoint**: `POST /api/v1/register/batch` with `{ agents: [...] }`, plus the binary-wire twin `REGISTER_AGENT_BATCH`. Bounded by `MAX_BATCH_REGISTRATION_AGENTS` (512).
- **Semantics, asserted rather than implied**: a batch is equivalent to registering each entry singly (traits, initial fear and `initial_position` all verified identical against the singular path); a **malformed entry is reported with its index and does not kill its valid siblings**; duplicate ids inside one request collapse to one registration with last-write-wins; an unusable envelope (non-object, no `agents` array, empty array) returns `400 VALIDATION_FAILED`; and an **over-limit batch is rejected, not truncated** — silently dropping registrations would leave agents unregistered, which is the failure the endpoint exists to remove.
- **Client**: both the showcase and packaged Godot clients send the whole pending queue in one request up to the cap, only mark server-**confirmed** ids as registered (requeuing the rest), disable batching permanently on a `404` so a pre-batch server is not retried against a missing route, and count `batched_registration_requests` / `individual_registration_requests` so batching is measured rather than assumed.
- **Evidence**: the live in-engine run (`run_showcase_live_conformance.gd`, 38 assertions, exit 0) measures **28 agents registered in 1 request with 0 individual round trips**; `verify_server_lifecycle.mjs` gained a batch section covering equivalence with the singular path, a 64-agent crowd, per-entry rejection with indices, duplicate collapse, all four envelope `400` cases, non-partial application of an over-limit batch, and both binary-wire paths including correlation-id preservation on error; `verify_godot_live_pipeline.mjs` (128 assertions) pins the client's batched path at source level. `AdapterConformance` now checks the verb and publishes a `registerBatch` canonical sample. See `evidence/batch_registration_2026-09-20.md`.
- **Scope boundary**: no performance or throughput guarantee is claimed — the claim is bounded and structural (a population of ≤ 512 agents registers in one round trip instead of one per agent). Singular `registerAgent` semantics are untouched; the route is additive. Not a rendering, Editor, or host-game claim. The measured bring-up figures are recorded in `evidence/session_bringup_2026-09-20.md` (`npm run measure:session-bringup`) as one machine's numbers for one workload, not a universal claim. The teardown and trauma-authoring halves of the control plane are covered in §19.

### 19. Batched Teardown, Batched Trauma Authoring, and the Session Ownership Contract (`ClaimArbitration`, `verify_server_reconnect.mjs`)
- **The bound is per request, not per verb**: one constant, `MAX_BATCH_CONTROL_ITEMS` (512), bounds `POST /api/v1/register/batch`, `POST /api/v1/unregister/batch` and `POST /api/v1/trauma/batch`, each with a binary-wire twin (`REGISTER_AGENT_BATCH`, `UNREGISTER_AGENT_BATCH`, `TRAUMA_ZONE_BATCH`). `MAX_BATCH_REGISTRATION_AGENTS` remains exported as an explicit alias of the single bound, not a second limit.
- **Three deliberate semantic choices**: `not_found` is a terminal, non-error outcome for teardown (reported separately anyway, because a client that could not distinguish it would requeue forever); duplicate ids collapse (last-write-wins for registration, idempotent for teardown); and an unusable **envelope** is a `400` while a malformed **entry** is reported with its `index` and its valid siblings still proceed. A batch whose every entry is malformed is therefore `200` with `count: 0` and the rejections enumerated.
- **Two silent-failure modes were found and closed**: rejected teardown ids previously vanished (leaving an agent live on the server while the host believed it was gone — now counted in `unregistration_rejections` and reported), and rejected trauma zones were invisible (now counted in `trauma_zones_rejected`, because partial application that looks like complete application is what a host cannot debug).
- **Session ownership closes the ledger's open host/session contract.** Agents were always preserved across a socket drop, but the server could not say *who* owned them, so "my host reconnected" and "a rival is claiming my crowd" were indistinguishable. One rule now applies per agent id: unclaimed → granted; same session → granted (the reconnect path, unconditional); owned by a **non-live** session → adopted; owned by a **live** session → refused, with nothing mutated, unless the claimant explicitly asks for `takeover`. A session is live while it holds an OPEN connection or has been heard from within `sessionStalenessMs` (default 30 s). A caller naming **no** session is granted unconditionally *and records no ownership*, so hosts that predate sessions behave byte-identically. Ownership gates **claims**, not observations or ticks: `RuntimeSimulation` never consults it and the per-tick hot path is untouched.
- **What happens to the abandoned connection**: its agents survive, its ownership survives, the session reads `attached: false` with a `detached_at` timestamp in `GET /api/v1/sessions`, and its agents are *still* not adoptable while it is inside the liveness window — but once it is not live they become adoptable, which is how a process that lost its in-memory session list recovers its crowd.
- **Evidence**: `verify_server_reconnect.mjs` proves the whole contract over **real loopback WebSockets** with two live sockets and two session ids competing for one crowd — rival refused per entry with the owner named and the agent's traits verified unmutated, agents *and* ownership surviving the owner's socket close, a rival still refused while the owner is warm, the owner returning on a new socket re-adopting its crowd with state preserved and no duplication, `takeover` transferring ownership and being counted, and teardown releasing ownership so the freed id is claimable again. `verify_server_lifecycle.mjs` covers the same rules without a listener plus the anonymous-caller compatibility case and reset semantics. `verify_godot_live_pipeline.mjs` (128 assertions) pins the client side, and the assignment-site guard was drift-tested: regenerating the client's session id per `_ready()` fails the probe. See `evidence/session_ownership_2026-09-20.md` and `evidence/batch_control_plane_2026-09-20.md`.
- **Scope boundary**: this is session **bookkeeping**, not a security boundary. Ownership governs claims, not reads — a tick is served whether or not the caller owns the agent, because the middleware stays advisory and the host keeps authority. `sessionStalenessMs` is a liveness heuristic, not a heartbeat protocol — a host silent for longer than the window while still running can have its agents adopted. No performance guarantee is claimed for the batched routes; the measured bring-up numbers are one machine's figures for one workload (`evidence/session_bringup_2026-09-20.md`). The two limits this section used to carry — that a `session_id` was the only identity a claimant had, and that sessions did not outlive the process — are both addressed in §20.

### 20. Session Identities (`session_token`) and Ownership Across a Middleware Restart
- **Name and credential are separated on purpose.** A `session_id` is a host-chosen *name*: it survives a host process restart, but anyone who has seen it can write it down, so on its own it is not a credential. A `session_token` is *server-issued*: 256 bits of CSPRNG entropy (`SESSION_TOKEN_BYTES = 32`), returned **exactly once**, when a session is established. The name says *which* crowd; the token says *it is me*. The guessing attack the name-only model allowed — a hostile client inheriting a live session's crowd by naming it — is what the token closes.
- **The rules, per claim**: matching token → granted, liveness irrelevant (the reconnect path, and the one that works across a middleware restart); name unclaimed → granted, new session, token issued; name claimed but the session is **not live** → adopted, a **new** token minted and the old one retired, so a displaced holder cannot return on it; name claimed and **live** → refused with nothing mutated; a token presented that does not match → a distinct, counted `REFUSED_TOKEN_MISMATCH` rather than a silent fall-through to name-only handling; `claim: "takeover"` → the explicit, counted displacement of a live owner.
- **Tokens are hashed at rest and compared in constant time.** Only a SHA-256 of each token is retained (`hashSessionToken`, `timingSafeEqual`), so neither `GET /api/v1/sessions` nor a snapshot can leak a credential — a snapshot carries `token_hash` values, never raw tokens, and is therefore **not a credential store**. No salt is used and none is needed: a 256-bit random token has no dictionary to build.
- **One identity per request, not per entry.** A batch resolves identity **once** (`establishIdentity`) and then arbitrates ownership per agent (`claimUnder`). This is not a style choice: the token for a *new* session is minted during identity resolution and only reaches the host in the response, so per-entry re-establishment would refuse every entry after the first — the client cannot present a token it has not been given yet. A refusal returns the token anyway, so a refused host is not left unable to prove who it is on its next attempt, and a refusal is `409 REFUSED` / `OWNED_BY_LIVE_SESSION` rather than a `200` with a lie.
- **Ownership across a restart.** Ownership is server-level state, so it rides in the snapshot as a server-level extension (`snapshot.sessions`) rather than inside the simulation's own schema. On load it is filtered to agents the snapshot **actually** restored (a recorded owner for an absent agent would refuse a host its own id for no reason) and existing ownership is cleared first (a load replaces the world). Every restored session begins **unbound**: `observed: false`, no connection, and — the point — therefore not live merely because the middleware restarted quickly. A restored session can never block the host it belongs to. A host that kept its token is recognised as a plain grant; a host that lost it adopts, because the incumbent is not live; a snapshot with no `sessions` field restores nothing and leaves legacy hosts byte-identical.
- **Evidence**: `verify_server_lifecycle.mjs` covers token issuance and rotation (adoption and takeover both mint a new token and retire the old), a refusal naming the live owner, the counted mismatch case, the batched single-identity path, snapshot save/load **including ownership**, and a dedicated *Ownership across a middleware restart* section that asserts ownership survives, affective state survives alongside it, a kept token is recognised as a plain grant, and a host without a token adopts. `verify_server_reconnect.mjs` proves the same contract over **real loopback WebSockets**. The Godot reference client adopts tokens (`_adopt_session_token`) from both handshake and batch responses and echoes them on every claim; `verify_godot_live_pipeline.mjs` pins those assignment sites, and the guard was drift-tested (regenerating the client's session id per `_ready()` fails it). See `evidence/session_ownership_2026-09-20.md`.
- **Scope boundary**: the token defeats *name guessing*, not traffic interception. The server is loopback-bound plain HTTP/WebSocket by default with no TLS, so an attacker who can read the wire can read a token — this is not authentication against a network adversary, and enabling remote access does not add transport security. Tokens now have a bounded life and an end the host controls (§22): `tokenTtlMs` expiry (7 days by default, `0` disables) that is honoured **once** and replaced in the same response rather than refused, `rotate_token: true` to retire a credential on demand, and `POST /api/v1/session/revoke` to end a session outright. They are still bearer credentials: whoever can read the wire can read a token, and possession is what the server checks. Restored sessions are unbound by design, so **an ownership snapshot is not liveness**: after a restart, liveness is re-established by the host actually speaking. Ownership still gates claims rather than reads, and a caller naming no session still records no ownership at all.

### 22. Credential Lifetime, Ownership-Gated Destruction, and the Refusal Drill-Down (`ClaimArbitration`)
- **Registration was arbitrated; destruction was not.** `POST /api/v1/unregister`, `/unregister/batch` and the WebSocket twins removed any agent for any caller, and `{clear_agents: true}` wiped the world for any caller. That made every claim rule beside the point: an attacker who could not steal a crowd could delete it. `authorizeTeardown(agentId, {sessionId, token})` and `authorizeReset({sessionId, token})` apply the same ownership test to the destructive verbs. Both are **pure decisions**: the caller releases on an `allowed` answer, so a refusal cannot half-apply. Unowned → allowed (this is exactly what every pre-session host still does); owned by the caller's **proven** session → allowed; owned by a session that is no longer live → allowed and reported as `RELEASED_OWNER_STALE`, which is the same window in which those agents are already adoptable, so cleanup grants an attacker nothing adoption did not; owned by a **live** session → refused, recorded, and named. A reset additionally refuses while *another* live session owns agents and names the blockers; a middleware restart is the deliberate way past a live owner's objection, because restored sessions are unbound and therefore not live.
- **A stranger could pin a session, and no longer can.** An earlier revision refreshed the incumbent's `lastSeen` on a refusal, on the reasoning that an incumbent whose name had just been spoken was probably still around. That reasoning was wrong: nothing a stranger sends can *shorten* the window (the window is a function of the incumbent's own silence), so the refresh could only ever *extend* it — a denial of service in which repeating a name keeps a crowd locked to a credential nobody, including an owner that lost its token, can produce. Liveness now moves on proven traffic only (`bind`, `bindIfProven`) and on the host's own proven claims; a refusal is inert.
- **The credential has a lifetime and a host-controlled end.** `tokenTtlMs` (7 days by default, `0` disables) bounds acceptance. An expired token is deliberately **not** a lockout: possession still proves identity, so the claim is granted *and* a fresh token is returned in the same response (`token_rotated`, `token_expired`). `rotate_token: true` on any claim retires a credential on demand, and is honoured only for an identity that **already matched**, so it cannot rotate a credential the caller does not hold. `POST /api/v1/session/revoke` ends a session on the host's instruction: the record goes, the name becomes free for a fresh claim, and its agents are **released but stay registered** — ownership ended, the host's crowd did not disappear. `404` for an unknown name, `403` for a wrong credential, `400` for a missing one: revoking on a bare name would have been the cheapest denial of service in the protocol.
- **A refusal is now an explanation, not a count.** `refusalLog` (bounded to 25, newest first) records the verb, the agent, the caller, the blocking session and a `retry_after_ms`; `refusals_by_reason` tallies them. `retryAfterFor` returns `null` when the blocker holds an open connection and a real countdown otherwise, because "no deadline" and "retry now" are different answers. The dashboard renders this at `GET /api/ownership` as `refusals[]` with a one-line `headline` and a `resolution` sentence, driving a second button on the Sessions tab — a count is an alert, this is a diagnosis. The endpoint stays read-only by construction: `POST` is a `404`, so the display layer has no arbitration path.
- **Making teardown gated exposed a real client defect.** Every adapter sent `session_id` when retiring agents and **none** sent the token, so a name-only teardown was correctly refused as a stranger's request and honest hosts were locked out of retiring their own crowds. The Godot in-engine run found it (a rival could not retire an agent it had adopted); the gap was then closed in Godot, Unity, C# and Python, and Suite 7 of `verify_adapter_conformance.mjs` pins the contract per adapter with bounded source windows, drift-tested by stripping the token line and watching the tripwire fail. The same pass found the Godot client clearing its local registered-agent view when a reset was *sent* rather than confirmed — a refused reset would have left the host believing a crowd was gone while the server still simulated it.
- **Evidence**: three new sections in `verify_server_lifecycle.mjs` (gated destruction across all routes and both transports with nothing mutated on refusal; the credential lifetime including rotation, expiry-as-rotation, and revocation semantics; and the refusal drill-down including a 60-refusal flood that cannot grow the log past its bound); a new hostile-host section in `verify_protocol_abuse.mjs` that also proves on the clock that name-spamming cannot hold a session live; the drill-down assertions in `verify_dashboard_endpoints.mjs` (verb, agent, caller, blocker, countdown, resolution, separately-explained teardown refusal, and the `null`-vs-`0` distinction); `verify_adapter_conformance.mjs` Suite 7 (210 assertions total); and the full in-engine Godot sweep re-run green (4/4 suites). See `evidence/credential_lifecycle_and_gated_destruction_2026-09-20.md`.
- **Scope boundary**: this is not authentication against a network adversary. Ownership is **continuity, not access control** — it protects a live session's agents from other sessions and nothing else, and there is still no transport security. Expiry bounds the useful life of a leaked credential; it is not revocation. A stolen token can revoke, which is inherent to revocation-by-credential. The refusal log is a bounded diagnostic, not an audit trail. And `RELEASED_OWNER_STALE` does let anyone clean up a dead owner's agents, deliberately, because that is the same window in which they are already adoptable.

### 23. Host Credential Persistence and Unity Behaviour Outside the Editor (`verify_host_token_persistence.mjs`, `verify_unity_adapter_behavior.mjs`)
- **The host obligation was the untested one.** Every earlier ownership probe holds the token in memory, so none of them could test what a host actually has to do: write the credential somewhere that outlives its own process and load it before the first claim of the next run. A host that loses its token is not broken — it adopts its own name once the previous session is not live — but it returns as a stranger to its own crowd, and only a **separate process** can tell that apart from a successful reconnect.
- **Godot, three engine processes, one store.** `tests/godot_project/run_session_persistence.gd` is phase-driven and `verify_host_token_persistence.mjs` runs it three times, with one store file between runs, restarting the middleware in between. Phase 1: the crowd registers in one batched request, the server issues a credential, the adapter writes it to disk **at the moment it exists**, and the first claim is `GRANTED`. Phase 2 (new process, same server): the identity is loaded rather than regenerated, the crowd comes back `GRANTED` with zero adoptions, and a tokenless rival is still refused both a claim and a teardown. Phase 3 (new process, server **restarted from a snapshot**): a credential hashed in a *previous server process* still proves continuity, a tokenless claim on the restored session is `ADOPTED` (a restored session is unbound, so it is not live), and the reset gate refuses an honest host a wipe that would destroy another live session's agent, then allows it once nothing live is in the way. 9/13/12 in-engine checks plus 19 probe assertions, including on the artifact itself: the store holds the session name and a 64-hex credential, and the server's own listing never contains it. Phase ordering was learned by failing — the rival must run *before* the returning host claims, or the host's own claim makes the session live and the rival is correctly refused instead of adopting.
- **Unity is now executed, not just compiled.** `tools/verification/unity/UnityEngineShim.cs` backs the UnityEngine surface with real behaviour (HTTP over `HttpClient`, field-based `JsonUtility`, real file and PlayerPrefs storage, a coroutine runner) and `UnityBehaviorHarness.cs` drives the **unmodified** adapter through its public API plus reflection, failing loudly if a field or method it needs is renamed. `verify_unity_adapter_behavior.mjs` builds them and runs four phases in four OS processes: phase 1 (15 checks) registers the crowd in one request, is `GRANTED`, writes the credential to a real file, is refused nothing for its own teardown and trauma, and watches a tokenless rival be refused both a claim and a teardown; phase 2 (7 checks) loads that file in a new process and is `GRANTED` with zero refusals — an assertion that only means something because phase 1's session is still live, so a name-only claim would have been refused; phase 3 proves the host with a **registered key** against a `required`-policy server and shows its own token alone being refused; phase 4 (new, §28) writes the credential **and the private signing key** through the encrypted store, shows a new client **adopting the stored key** rather than generating one, and has the Node reference read the same file back from outside the adapter. The probe also asserts server-side truth: the crowd is credited, the host can prove continuity, claim and teardown refusals land in **separate** server tallies, and the stored credential never appears in the ownership listing. `Runtime/FearSessionStore.cs` provides `ISessionStore` with `InMemorySessionStore` (the default), `FileSessionStore` and `PlayerPrefsSessionStore`, plus `FearEncryptedSessionStore` (`ISecretSessionStore`, §28) which carries the signing key too and is the store that is **unreadable at rest**; persistence is opt-in and off by default, and the plaintext stores remain because a host with nowhere to keep a keyring is better served by an honest plaintext option it can see reported than by a silent downgrade.
- **The old compile check's stubs were actively misleading.** `JsonUtility.FromJson<T>` returned `Activator.CreateInstance<T>()` and `responseCode` was hardcoded to `200`, so every control-plane path read as a success and a compile pass proved nothing about behaviour. Both probes now compile the adapter against the **same** shim, so the compile gate and the behaviour gate cannot drift apart.
- **Scope boundary**: the lifecycle *bodies* are now driven by the shim in Unity's order (§36), so the adapter's `OnEnable`, `Start`, `Update`, `OnDisable` and `OnDestroy` are no longer shipped unexecuted — but WHEN Unity calls them is still an Editor question, coroutines run to completion synchronously instead of across frames, the shim is an implementation rather than Unity's own API, and `FearAgent.cs`/`FearAgentHUD.cs` are covered by neither probe. No in-Editor run has been performed, so the Unity row stays `PARTIAL` with the `IMPLEMENTED_NOT_EDITOR_VERIFIED` qualifier. Godot persistence proves the credential round-trips; it does not make the store safe on a shared machine. Nothing here generalizes to Unreal or to a universal multi-engine claim. See `evidence/host_token_persistence_and_unity_behavior_2026-09-20.md`.

### 24. Request Signing (RS256) — a leaked session token stops being sufficient (`packages/runtime/src/RequestSigning.js`, `packages/runtime/src/RequestSigner.js`, `tools/verification/verify_transport_signing.mjs`)
- **The bearer-token limit is the one this closes.** Every ownership section above ends with the same sentence: a session token is a bearer credential, so whoever holds the string can act. The token is exactly the thing that escapes — a snapshot, a log line, a crash dump, a backup, another process. Request signing adds a second factor the wire never carries: a **host-generated** RSA-2048 keypair, with only the public half given to the server, and a signature over the exact request bytes so a captured request is worthless.
- **RS256 because it is the one asymmetric primitive every language here already has.** Node's `crypto`, Godot's `Crypto.generate_rsa`/`sign`, .NET's `RSA.SignData`, Python's `cryptography`. Ed25519 is smaller and would have been nicer, but Godot's `Crypto` does not expose it and neither does the .NET 8 BCL — and an adapter that cannot sign is an adapter that silently falls back to a bearer token. Interop was **verified before the design was committed to**: a signature produced by the real Godot 4.6 binary verifies in Node against the PEM Godot exported.
- **The canonical input is defined byte for byte**, with an explicit version tag: `FEAR-AI-SIGN-V1`, `HTTP`, the uppercase method, the request target as sent, the SHA-256 of the raw body, the session id, `issued_at` as decimal milliseconds, and a nonce, each line ending in a single LF including the last. Method, target and body hash are all covered, so a signature cannot be moved between verbs or routes or survive an edited body. **The trap, found by failing**: Godot's JSON parser returns numbers as floats, so `str(issued_at)` produced `1758400000000.0` and every signature was refused as `SIGNATURE_INVALID` — a symptom that looks exactly like a broken key.
- **WebSocket authenticates once, against a server-issued challenge.** Per-frame signing would put an RSA signature on every simulation step, so a connection answers a single-use challenge instead. That is strictly stronger than a client-chosen nonce (nothing to capture and re-send, no clock to trust), it costs one signature per connection, and it composes with the existing model because the connection is what `bind`/`bindIfProven` already attach to a session.
- **Three policies, and the default is not `required`.** `off` ignores signatures entirely; **`preferred` is the default** — a caller that *presents* a signature must present a valid one (malformed, stale, replayed and forged are all refused and **never** silently downgraded to the bearer path), while a caller that presents none is judged by the token rules as before; `required` makes the token alone insufficient for any request or connection that **names a session which has a registered key**. `required` is scoped to keyed sessions on purpose: a host that never registered a key cannot be locked out by a flag it did not ask for, and an anonymous caller owns nothing. `preferred` is safe to leave on everywhere because it cannot break a host that does not sign and cannot be used to bypass anything.
- **Two rules that took a failure to get right.** The **first** claim cannot be signed — no session exists for the signature to belong to — and that claim is the one carrying the public key, so refusing it would leave the host unable to ever establish one; signing starts only after the server **confirms** the key. And **rotation takes two proofs**: a token-only caller must not be able to install its own key, or stealing a token would upgrade into a permanent takeover that locks the real host out; under `required` the gate refuses an unsigned rotation before arbitration sees it, and the token holder can rotate only while also proving the **current** key. Both directions are asserted.
- **The server gate is one pure decision taken before any route runs**, so nothing is mutated on a refusal, and failures are counted by reason into the same refusal log the dashboard already explains: `SIGNATURE_MISSING`, `SIGNATURE_MALFORMED`, `SIGNATURE_UNSUPPORTED_ALG` (refused, never ignored), `SIGNATURE_UNKNOWN_KEY`, `SIGNATURE_STALE` (two-minute skew), `SIGNATURE_REPLAY`, `SIGNATURE_INVALID`, and the two challenge reasons. The replay check runs **before** the signature is decoded or verified, so a resend loop is cheap to refuse — which means a malformed signature carrying an already-accepted nonce reports `SIGNATURE_REPLAY`, and the probe asserts the classification that actually occurs rather than the one that reads better. A nonce is remembered only after a valid signature, so junk cannot fill the cache and evict a nonce an attacker wants to replay.
- **All five clients sign the same bytes**, and the C# implementation was rewritten onto the **oldest** surface that ships (no `ImportFromPem`, no `ExportSubjectPublicKeyInfoPem`, no `Convert.ToHexString`, an instance `RandomNumberGenerator`, a hand-built SPKI DER) because the compile gate caught the first version using .NET 5-only members on the `netstandard2.0` target the standalone client builds for.
- **Evidence**: `verify_transport_signing.mjs`, **61 assertions** — the 15-case decision matrix (including that `rejected` is not derived as `accepted - verified`, a real defect that had been reporting every *unsigned* legacy request as a rejection); 22 live-server policy assertions covering the leaked token alone being refused with nothing mutated, the signed replay being refused, a signed read being gated, an anonymous caller being untouched, a stranger being unable to replace a registered key, and a leaked token being unable to install one; 7 WebSocket handshake assertions including a challenge that cannot be answered twice; 6 restart-continuity assertions (the snapshot carries the public key and **no private material and no token**); a **measured** 0.62 ms per RS256 verify over 200 samples on the control plane only; and 10 cross-language assertions in which the **Python client and the Godot adapter in-engine** each register a key, sign, and are never refused, with the server confirming the fingerprint each one built.
- **Scope boundary**: this is **not TLS and not confidentiality**. Payloads stay plaintext and a wire reader still sees every observation, advisory and agent id. It authenticates requests and makes them non-replayable, and that is all. The **binary wire carries no session identity at all**, so a key cannot gate it — stated rather than implied. Key persistence is still a host decision because it commits a host to keeping a private key, but the key itself is no longer written in the clear: it goes into the encrypted store container (§28), so the previous limit "a persisted private key is unencrypted" no longer holds, and what replaces it is narrower — the container protects a copied **file**, not a machine (§28 states both). There is no per-route scoping.

### 25. Identity Audit Timeline (`packages/runtime/src/ClaimArbitration.js` `eventLog`, `GET /api/ownership` → `timeline[]`, `tools/verification/verify_dashboard_endpoints.mjs`)
- **A refusal log answers the wrong question.** It answers "why was my NPC not registered". A host that lost its crowd is asking "what happened to my session", and that answer usually **begins with a grant it did not expect**. So the arbitration layer carries a second bounded ring: `timeline[]` newest-first, `EVENT_LOG_LIMIT` = 100, with `events_recorded` a monotone counter that keeps rising past the ring so "the last 100" is honest rather than "all there were", and `timeline_scope: 'THIS_PROCESS'` stating that the ring is deliberately **not** part of a snapshot — an empty timeline after a restart must not read as "nothing happened".
- **Rows are a name, an id, an outcome and a timestamp — no token, no signature, no key body**, so the timeline rides on the same token-free surface as the rest of the ownership view. Four kinds are recorded: an `identity` decision with the **proof** that held (`new_credential_issued` vs `presented_valid_token`, plus rotation/expiry); a `claim` **per agent** (a batch of 512 is one identity decision and 512 ownership decisions, and "which NPC did I lose" needs agent granularity); a `signing_key` registration or replacement carrying the **fingerprint only**; and a `revoke` with the number of agents released.
- **Refusals join the same stream from inside `_recordRefusal`**, which every refusal path already funnels through. Hooked there rather than at each call site, so a new refusal path cannot forget to be on the timeline, and a refused row is rendered by the **same** explainer the drill-down uses, so the two descriptions cannot drift.
- **The dashboard renders it**, not just the JSON: `GET /api/ownership` returns `timeline[]` with a `meaning` per row (`info` / `granted` / `recovered` / `handover` / `refused`) and a one-line `headline`, and the Sessions & Ownership tab gained an **Audit Timeline** button. An empty timeline explains that its scope is this process and that a snapshot-restored server keeps its sessions but starts with an empty ring.
- **Evidence**: the timeline section of `verify_dashboard_endpoints.mjs` — 7 ordered decisions with grants and refusals on one stream asserted **newest-first**; the **oldest** granted identity row checked via `.pop()` rather than `.find()` on a newest-first list (the first draft asserted the wrong end of an ordered ring, which is the mistake this probe exists to catch elsewhere); a credential-proven grant distinguished from a fresh name claim and asserted **not** to report a newly issued token; one granted per-agent claim at agent granularity; a refused claim's timeline headline asserted **byte-identical** to the drill-down's; every row having a headline and a renderable `meaning`; no token-keyed **string** field anywhere in the timeline; and 204 decisions in a separate arbitration object leaving the ring at exactly 100 rows with the oldest evicted, the newest kept, and the counter still rising.
- **Scope boundary**: a per-process diagnostic ring, not a durable audit log, and not tamper-evident. Bounded because anything that can reach the claim path can write to it.

### 26. Adversarial Fuzz of the Ownership Layer (`tools/verification/verify_fuzz_arbitration.mjs`) — seeded and replayable
- **Hand-written scenarios test the cases their author thought of**, and every interesting bug in this layer has been of the other kind: refreshing the incumbent's liveness on a *refusal* turned name-spamming into a denial of service that no happy-path probe would have noticed. The fuzzer exists so that class of defect is found on purpose.
- **Seeded (mulberry32), with the seed printed**, so a failure is reproducible from one number — and section 2 proves the seed is load-bearing by checking that the same seed reproduces the identical decision trace and a different seed does not. 4,500 operations across three seeds run against the arbitration object with an **injected clock** (staleness and adoption are only reachable by moving time), plus 240 operations across the live HTTP control plane.
- **Five invariants, checked after every operation**: **I1** a refusal is inert (a denied claim, teardown, reset or revoke leaves ownership byte-identical); **I2** a stranger cannot reach a live crowd (no take, remove or wipe of a **live** session's agent by an unproven caller, while a quiet session's agent may still be cleaned up); **I3** a credential is not a name (a grant not accompanied by a fresh credential had to be proven with the **current** one); **I4** conservation (owned agents == sum of per-session counts == agents with a recorded owner, after *every* operation); **I5** a revoked credential is worthless.
- **Two findings from building it were the probe being wrong, not the code**, and both are recorded because that is the more common shape of a fuzz "failure". The first world fingerprint included the set of **session names**, so it flagged a legitimate case: a claim refused at the per-agent step still **creates** the claimant's session row with zero agents, which the dashboard probe asserts is *correct* behaviour — the invariant is about who owns what, not which names have been heard. And a blanket "this verb reduced ownership" check was wrongly applied to teardown, revoke and reset, which are *supposed* to release agents; it now applies to `claim`, which may only ever add.
- **The fuzzer drift-tests itself**, because a probe that cannot fail proves nothing: it drives a deliberately **broken** arbitration (a refusal that mutates) and requires the inertness check to fire, then drives a **half-applied** release and requires the conservation check to fire. The first version of that second check claimed conservation was sensitive to a *consistent* release — it is not, and the claim was wrong rather than the check.
- **The live tier** additionally asserts no 5xx and no undeclared status across 240 mixed operations, that the server's own summary stayed self-consistent, and the sharpest form of the liveness rule: a name-only caller knocking 40 times was **never handed a credential for the live session**, gained no agent, and left the owner's own teardown working.
- **Scope boundary**: single-threaded and sequential, driven one decision at a time the way the server drives arbitration. It says nothing about concurrency, timing, or the WebSocket envelope path, and the tick hot path never consults ownership at all.

### 27. Unity EditMode Tests — Run Outside the Editor, Gated Inside One (`tools/verification/verify_dotnet_adapters_compile.mjs` Section C, `tools/verification/unity/NUnitTestRunner.cs`, `tools/verification/helpers/editmode_fixtures.mjs`, `tools/verification/verify_unity_editor_tests.mjs`)

What changed is that the EditMode test project now **exists** (Editor-only, `UNITY_INCLUDE_TESTS`-guarded, referencing `FearAI.Runtime` plus both test-runner assemblies), that its five fixtures are **compiled on this machine**, and that a runner can execute them anywhere an Editor is installed.

- **The fixtures are now compiled AND RUN outside the Editor** (`verify_dotnet_adapters_compile.mjs` Section C, **27 checks**), against the UnityEngine shim plus a minimal NUnit surface (`tools/verification/unity/NUnitShim.cs`) whose assertions are **real implementations rather than no-ops** — a stub `Assert.IsTrue` that checks nothing is the defect that made the old Unity compile gate meaningless. Four things make its green mean something rather than merely appear. (1) Before it runs a single fixture it must pass its **own self-test**, which requires it to distinguish a pass, an assertion failure, an unexpected exception and an `[Ignore]` — a runner that swallows exceptions prints the same green summary as a perfectly correct suite, and its ability to say "failed" is the precondition for reading "0 failed" as a result. (2) The number of cases it ran is compared against the count **derived from the test sources** by `tools/verification/helpers/editmode_fixtures.mjs`, and its fixture roster against the roster derived the same way, so 39 of 41 tests cannot pass as 39. On this machine: **41 cases over 5 fixtures, 0 failed, 0 ignored.**

That assertion had survived review, a compile and every gate this repository had, because **nothing had ever run it**. It is now `Assert.AreEqual(0, algorithmReader.Tagged(0x05).Length, …)` — the same claim (tag `0x05`, zero length, i.e. an explicit NULL) without the encoding misconception — and reverting it to the broken form is one of the mutations the drift test requires to fail.

Both gates now read the roster and the `[Test]` count from one helper, so the run outside the Editor and the run inside one cannot hold different ideas of which fixtures exist; the Editor probe also now requires the Editor to have run **at least as many** cases as the sources declare, so a fixture that compiled while its tests never ran cannot hide behind a green `failed 0`.

What the outside-Editor run proves is that each fixture body executes and its assertions hold against **this repository's implementations** of UnityEngine and NUnit; it proves nothing about whether Unity's own `nunit.framework` and API behave the same way, and the shims' divergences are unchanged (a shim method that returns synchronously where Unity yields, a `PlayerPrefs` that is a dictionary rather than a registry). The EditMode tests are not a player build (a different scripting profile), not frame scheduling, not MonoBehaviour lifecycle, and nothing rendered. `FearAgent.cs` and `FearAgentHUD.cs` remain outside every probe. ### 28. The Persisted Credential and Signing Key, Unreadable at Rest (`packages/runtime/src/EncryptedStore.js`, `packages/adapters/godot/fear_encrypted_store.gd`, `packages/adapters/unity/Runtime/FearEncryptedStore.cs`, `tools/verification/verify_store_encryption.mjs`)
- **The limitation it closes was written down, not hidden.** §24 ended with "payloads stay plaintext... a persisted private key is **unencrypted**", and §23 ended with "the store is a plaintext bearer credential". Both were pointing the wrong way: a private key on disk is what protects the crowd against a lifted token, and writing it in the clear handed an attacker the **stronger** of the two credentials — in a file that lives inside the game's own save tree, i.e. inside every backup, synced folder, support bundle and crash dump. The credible leak was never a shell; it was a folder that got copied.
- **One container, three writers, byte-identical.** `FEAR-AI-STORE-V1`: PBKDF2-HMAC-SHA256 into two labelled keys, AES-256-CBC with the PKCS#7 applied **by the format rather than the library**, and an HMAC-SHA256 over every byte from the file start through the newline ending the `ct=` line. `iter` is read from the file rather than assumed. `name` is deliberately plaintext — the ownership model already rests on a name not being a credential (§20), so it costs nothing and answers "which host is this?" for a stray store — and it is inside the MAC, so it cannot be edited. `capability` in Node, GDScript and C# all produce that container, and the probe requires **bit-identical** output for pinned inputs, because a format that only has to be self-consistent can be lenient on read.
- **Three interop traps, all found by running it.** (1) **Padding is the caller's job**: Node pads PKCS#7 automatically and Godot does not — and Godot's `AESContext` returns **zero bytes** for a non-block-multiple instead of erroring, so a 32-byte plaintext became 32 bytes on one side and 48 on the other. (2) The MAC covers the text **as sent**, so there is no canonicalisation step for two languages to disagree about. (3) **JSON key order is not portable**: Godot's `JSON.stringify` SORTS keys by default and Node emits insertion order, so keys, values and length were all correct and the ciphertext still diverged from its **second base64 character** — which presents exactly like "the other runtime used a different key". The payload is now canonicalised on all three sides (sorted keys; Godot's `sort_keys` passed **explicitly** rather than relied on). Only bytes inside the ciphertext changed, so a reader — which parses JSON and does not care about order — still opens older containers.
- **On by default, with the failure mode chosen deliberately.** Turning persistence on now means turning encryption on; nothing has to be asked for. If no keyring can be resolved the adapter **refuses the write and reports why** rather than falling back to plaintext, and only an environment with no keyring path at all can reach the explicit `allow_plaintext` opt-out — a keyring that exists but will not parse is refused, because that one may be recoverable. A host that opts out gets `PLAINTEXT_BY_REQUEST` back from the reported protection level, and the legacy form is read, reported as `PLAINTEXT_LEGACY`, and rewritten encrypted **in place** by the ordinary save on the next credential issue. A store that is already exposed is not made safer by being unreadable to its owner.
- **The keyring is a different file in a different tree.** A user-scoped configuration path (`%APPDATA%/FearAI`, `~/.config/fear-ai`, `~/Library/Application Support/FearAI`) by default, overridable by `FEAR_AI_KEYRING` or the adapter's own path setting, while the store stays wherever the host puts it. That is the whole relocation claim, and the probe asserts it directly: a container opens with the keyring that made it and **a copy of the store without that keyring is inert**.
- **Evidence.** `verify_store_encryption.mjs` (`npm run verify:store-encryption`, **46 assertions**): the credential and key absent from the file **bytes**, the name present and readable through the supported accessor, padding actually exercised, and a full refusal surface (wrong passphrase, edited plaintext name, one flipped ciphertext character, truncation, empty file, foreign version, downgraded cipher, newline in the name) each refused **for a reported reason**; then the real **Godot 4.6 engine** decrypts the reference container, exercises the same refusals, and writes one that is **bit-identical** to Node's; then the **C# container** — compiled and RUN with no Unity Editor installed, which is why it was kept free of any `UnityEngine` dependency — does both and matches byte for byte as well. `verify_host_token_persistence.mjs` grew from 3 to **6 engine processes and 44 assertions**: the restart evidence is the same evidence, now read against the encrypted file, plus a **new phase 5** that turns signing on, writes the private key through the container, and asserts a second client reads it back **verbatim** — with Node independently importing the recovered PEM and checking it against the public half stored beside it. `verify_unity_adapter_behavior.mjs` (37 assertions, 4 processes) added phase 4, where the real adapter writes credential **and** `FEAR-AI-RSA1` key through `FearEncryptedSessionStore`, a new client **adopts the stored key** instead of generating a new one, and the probe reads the same file back with the Node reference.
- **Scope boundary**: this protects a leaked **file**, not a leaked **machine** — anyone who can read both the store and the keyring can decrypt it. There is no TPM, no OS keystore, no per-user ACL, and the adapters set no file mode on Windows because there is no mode to set there. Python and the standalone C# client have no store at all (neither persists a session credential), and Python's host-directed `key_path` PEM is still a plaintext private key by the host's own choice. The Unity row keeps `IMPLEMENTED_NOT_EDITOR_VERIFIED`: the container is compiled by the compile gate and executed by the behavioural harness, both outside the Editor. Nothing here is confidentiality on the wire, and the binary wire still carries no session identity. See `evidence/session_store_encryption_2026-09-20.md`.

### 31. Flake Detection, a Digest-Pinned Engine, and a Roster That Says What Its Green Means (`tools/verification/run_probe_suite.mjs`, `tools/ci/fetch_godot.ps1`, `.github/workflows/test.yml`)
- **The suite now checks its own determinism, because a single run cannot.** §30 records a real flake (`verify_transport_signing.mjs`, failing 2 of 4 observed runs before its bind-race fix). Fixing one instance is not a proof about the class: repetition is the only thing that observes it. `--repeat <n>` runs each probe up to n times and calls it `STABLE` only if every run agreed, `FLAKY` if they disagreed, with `FLAKY` counted as a failure and exiting 1. A disagreement ends that probe early — a verdict that already differs needs no further samples — so `--repeat 3` on a flaky probe reports two verdicts, not three, and the wording says "up to n×" rather than claiming runs it did not make. The JSON report changes kind (`recorded-probe-stability-run`, with a per-probe `verdicts` array) so a repeated run can never be mistaken for the single-run recording the release dossier is generated from.
- **Determinism is checked on a clock, not on every push.** A third CI job, `probe-stability`, runs `npm run verify:probe-stability` (`--repeat 3`) nightly via `schedule` and on `workflow_dispatch`, and never on push: a flake is by definition invisible to the run that missed it, and tripling the suite on every pull request buys latency instead of signal. It fetches the same pinned engine and declares the same `FEAR_AI_EXPECT_PROVEN`, so its in-engine halves are exercised rather than skipped, and it uploads `probe-stability-report` with `if: always()`, because in the run that failed the sequence of verdicts **is** the evidence.
- **Proven by a probe that was built to lie.** A throwaway probe alternating verdicts on a counter, run with `--repeat 3`, reported `FLAKY … PASSED FAILED`, `1 failed`, exit **1**, and the report recorded `["PASSED","FAILED"]`. A stable probe reported `STABLE` with `["PASSED","PASSED","PASSED"]`. The probe was deleted in the same command.
- **The gate keeps the repetition honest.** `probe-stability-is-wired-and-repeats` asserts the npm script still repeats (`/run_probe_suite\.mjs --repeat [2-9]\d*/`). Without it, an edit to `--repeat 1` would leave the nightly job green, uploading a report, proving nothing about determinism — the exact shape of rot §29 exists to catch. The stability command is in the CI allowlist and the three-job contract is stated in `docs/SYSTEM_MAP.md`, so the map and the workflow are compared rather than merely adjacent. Gate total: **24 checks** as of §32 (**19** when this section was written; §31 added `stability-comparison-is-wired` and `unity-editor-gate-is-inert-until-configured`, the reviewed-change step below took it to 22, and §32 added `gate-inputs-are-committed` and `ci-npm-scripts-resolve`).
- **The engine CI installs is verified against two independently published digests.** `tools/ci/fetch_godot.ps1` checks the archive against the release's own `SHA512-SUMS.txt` digest (`3b2f0b4b…`) **and** the SHA-256 GitHub serves for the uploaded asset (`5c917762…`) **and** its byte size (79,418,197), deleting the file and failing on any mismatch. The job installs a binary and then executes it: HTTPS authenticates the transport, not the bytes, and a substituted asset under the same tag would arrive looking equally trustworthy while invalidating the recorded in-engine evidence that names this version. A mismatch is therefore treated as a substituted artifact rather than a flaky download. Both directions were exercised: a fresh download satisfied all three checks and produced an engine reporting `4.6.stable.official.89cea1439`, and a deliberately wrong digest against a 1,149-byte file reported `size expected 79418197, received 1149`, deleted the download and exited 1 with nothing left behind.
- **A space in an ancestor directory breaks the engine on a byte-perfect binary, and that is now checked instead of documented.** Extracting the engine into a directory inside this repository produced `CreateProcess failed, error 193` ("not a valid Win32 application") from a binary whose bytes run correctly elsewhere and match the published digests. Copying the identical bytes to four paths isolated the variable: a space in an **ancestor** directory fails, a space in the engine's own leaf directory does not, and no space works. Godot's `_console.exe` is a 198 KB wrapper that relaunches the real binary, and that relaunch is what breaks. CI is unaffected (`D:\a\fear-ai-sim\fear-ai-sim`), but this repository's own working copy lives under `...\lains Tools\...`, so the script now refuses a destination containing a space with the reason in the message — failing at the cause rather than letting an in-engine probe fail or time out three minutes later. The pre-existing engine the recorded evidence used (`C:\tools\02-Dev\godot`) reports the same version from the same build, so no recorded artifact is affected.
- **The roster states what its green means.** The runner prints the engine environment in its header and records it in the JSON (`engine`): `FEAR_AI_GODOT=<path>`, `… (MISSING FILE …)`, or that the variable is unset and the in-engine probes fall back to their own discovery. The last form is deliberately not a prediction of a skip — every recorded Windows artifact was captured with no `FEAR_AI_GODOT` set — because a summary that contradicted its own NOT PROVEN list would be a new lie in the place people read first. The GitHub step summary gained the same line plus the repeat rule when the run is repeated, so a reviewer of the nightly job sees the stricter contract rather than inferring the per-push one.
- **The dossier states its own determinism, including where it has none.** `docs/RELEASE_CANDIDATE_CERTIFICATION.md` gained a second generated block, rendered from `evidence/probe_stability_report.json` by the same generator as the roster (drift-checked, and the release-claim probe now requires the section to exist). It reports the recorded date, machine, engine and repeat count; a per-probe table with the **runs actually observed** (a disagreement cuts that probe short, so the column can read 2 where the repeat count is 3) and the verdict sequence (`3× PASSED`, or the raw sequence marked `FLAKY`); the count of repeated probes that agreed with themselves against the count that proved their claim — a probe can be perfectly repeatable and still prove nothing, and repeating a declared skip does not turn it into a pass; and **every probe in the recorded single run that was never repeated at all**, named individually. Absence is rendered rather than hidden: with no artifact, or with an artifact that is not a repeated run (`kind`/`repeat` checked), the section says so and lists **all 25 probes as never repeated** instead of omitting itself — an omitted section would read exactly like a clean one. The recorded repeated run itself is a real `--repeat 3` pass of all 25 probes: 25 of 25 gave the same verdict on every attempt, 24 proving their claim and 1 (`verify_unity_editor_tests.mjs`) reporting its declared skip three times over.
- **Each night is now compared to the recording, and every night is kept.** `npm run verify:stability-regression` (`tools/verification/stability_regression.mjs`) closes the two gaps a single night leaves. It compares the fresh repeated run against the committed recording and fails on three kinds of regression: a probe that was repeatable and is **intermittent now** (naming the sequence it used to give and the one it gives now), a probe that now **fails** consistently, and a probe that has **lost the proof the recording recorded** (`PASSED` → anything else, which is either a broken probe or an environment that lost what it needs). A probe present on only one side is reported as **suite drift** and not failed — a suite that legitimately gained or lost a probe is not a regression, and treating it as one would be a gate that cannot pass. A missing or wrong-kind artifact (`kind`/`repeat` checked) exits **2** with the command that produces one, rather than comparing two things that are not comparable. CI's nightly job runs it with `if: always()`, so the run that went red is the one that says which probe changed.
- **The ledger is what makes an intermittency rarer than the repeat count visible.** Because three attempts catch a defect that fires a third of the time and nothing rarer, every repeated run is appended to `evidence/probe_stability_ledger.jsonl` — one JSONL entry per night with each probe's verdict sequence — and the aggregate question is asked of the whole file: across all recorded nights, how many attempts has each probe made, and on how many nights did it disagree with itself? Tonight's clean run stops being "stable" and becomes "never observed disagreeing in 75 attempts across 1 night". It still bounds its own claim in the same breath: the absence of an observed disagreement in a bounded sample is not a proof of determinism, and a probe that has never disagreed may still be broken. A malformed ledger line exits 2 rather than being skipped, because silently dropping a night would hide exactly the gap the ledger exists to expose, and appending the same recording twice does not double-count it. **Ledger flakiness is reported and never gated** — a recorded fact cannot be failed away, and a job that ran red every night because of one would teach everyone that red means nothing — while the dossier's determinism section renders those probes in an *ever intermittent* table with their night and attempt counts.
- **The ledger's durations now catch a second family of defect.** Every entry already carried each probe's `durationMs`, so a probe that quietly became much slower was visible to the record and looked at by nothing. `timingComparison()` — one implementation, shared by the nightly gate and the dossier generator — compares a night against a baseline drawn from **earlier nights on the same platform and Node major only**, because a ratio across two machines measures the machines; a cross-platform ratio is refused as *incomparable* rather than guessed. The gate is ≥ 3× from a baseline ≥ 500 ms with a delta ≥ 1000 ms — the floors exist because a 40 ms probe becoming 400 ms is otherwise a "10× regression". Much **faster** than baseline is reported and never gated: a cache explains it, and so would a probe that stopped doing the work it used to do, and choosing between those stories without evidence is the kind of unfalsifiable claim this ledger keeps removing.
- **The flake rate is measured, and only the measurement is gated.** A night is a Bernoulli trial (the probe agreed with itself or it did not), and a night's attempts are not independent — the early exit on disagreement makes flaky nights *shorter*, so a per-attempt rate would be biased exactly where it matters. So the rate is disagreement-nights over nights, with a **95% Wilson score interval**: Wilson rather than the normal approximation because k is usually 0, where that collapses to zero width and would turn "never seen disagreeing" into "cannot disagree". The bound is the honest headline — one clean night bounds a probe's rate at **79.3%**, five at **43.4%** — and it is printed in the dossier beside the clean result. The gate fires at **≥ 20% over ≥ 5 nights** and not before: a single flake stays an incident that is reported, while a rate is a property of the probe. Two flake-driven gates can now fail the nightly job (a verdict regression in tonight's run, and a rate crossing that threshold) and one can fail it on time (a comparable slowdown), and every one of them names the probe and the numbers.
- **A night enters the record through one reviewed command.** The ledger only earns its keep if nights accumulate, and only CI can produce them — so `npm run fold:stability-ledger -- --from <artifact>` (`tools/verification/fold_stability_ledger.mjs`) folds a downloaded ledger artifact in, **dry run by default**: it validates, lists the new nights, flags any night on which a probe disagreed with itself, notes nights that carry no per-run durations, and prints the ledger's nights/attempts and each affected probe's rate with its Wilson interval **before and after** — then `--write` applies it, so reviewing and applying are one command with one flag between them. Refusal is the default posture for a write into the authority record: a malformed entry, a truncated artifact, an entry that is not a repeated run, an empty file, or an entry naming a probe absent from the committed recording all **exit 2 rather than being skipped**, because a dropped night or a foreign probe rewrites every denominator; an entry already present is skipped, so folding an artifact twice cannot inflate the counts; and a night that makes a probe look worse is never refused — that is the finding, and the nightly job already gated it.
- **A step is not the only shape a timing regression takes.** The runner now records each probe's **per-run durations** alongside the night's total, and `durationDrift()` pools them across comparable nights: a probe is drifting when the median of its **most recent two** comparable nights is at least **1.5×** the median of the earlier nights **and** above its own pooled **p90**, from a baseline ≥ 100 ms. It is a distributional test rather than a ratio of two numbers, because a probe that creeps 10% a night never trips the 3× step gate and is obvious here; a rise that stays inside the probe's own spread is reported as **RISING, never gated**; fewer than **4 comparable nights** is "not yet measurable" rather than a weak claim; and nights recorded before per-run durations existed are **excluded from the pool and the exclusion is printed**, because a sample that quietly shrank is the kind of silence this ledger exists to break.
- **Recording order is enforced, and one night had to be repaired.** Because the release-claim probe runs the dossier generator's `--check`, *any* new recording invalidates the dossier until it is regenerated — so recording a suite run and then a repeated run in one sitting made the release-claim probe fail **inside** the second recording. The order is record → regenerate → record → regenerate, and the failure mode is real: the ledger briefly held a night whose `verify_release_claim_boundaries.mjs` verdicts were `FAILED, FAILED, FAILED`, which is a **bookkeeping** failure (the dossier was stale when the probe ran), not a middleware defect. That night was removed from the ledger and re-recorded cleanly, and the removal is stated here rather than being an edit nobody can see. The committed ledger therefore holds **two** nights — `2026-09-21T03:44:24Z` (recorded before the runner emitted per-run durations, so excluded from the pooled sample and counted as such) and `2026-09-21T04:11:51Z` — 150 probe attempts, no probe ever observed disagreeing, and a 95% Wilson bound of **65.8%** on any probe's flake rate. That last number is why the fold command exists.
- **The Unity Editor gate is wired into CI, and deliberately inert.** A fourth job, `unity-editmode`, runs `npm run verify:unity-editor` — the EditMode tests in a real Editor — but only when the repository variable `UNITY_EDITOR_AVAILABLE` is `true`, on `${{ vars.UNITY_RUNNER || 'windows-latest' }}`, with the Editor path passed through `vars.UNITY_EDITOR`. The gate is not caution for its own sake: no GitHub-hosted runner has a Unity Editor or a license, so a job that installed one would need a license secret this repository does not have, and a job that ran unconditionally would be red on every push forever — the exact defect §29 removed. Until a runner is provisioned, the job is excluded by its own `if:` and **proves nothing**, which this section, `docs/SYSTEM_MAP.md` and the release dossier all state rather than leaving the row looking verified. When it runs it sets `FEAR_AI_UNITY_REQUIRED=1`, so a missing Editor is a failure rather than a comfortable skip, and `verify_unity_editor_tests.mjs` already fails on a red test, a missing results file, or **zero tests executed**. `unity-editor-gate-is-inert-until-configured` asserts both markers, so the job can neither become unconditional nor quietly lose the strict flag. **No Unity Editor has executed these tests**: the EditMode sources are now compiled **and run** outside the Editor by `verify_dotnet_adapters_compile.mjs` against a shim plus a minimal NUnit surface (`tools/verification/unity/NUnitTestRunner.cs`), which catches a fixture body that could never pass and cross-checks what ran against what the sources declare — but running them against the shims is not running them in Unity, so the Unity adapter row is not promoted by any of this.
- **A night is now proposed as a reviewed change, because a record that only grows when a human remembers to download an artifact bounds nothing.** The bound on a probe's flake rate is 79.3% after one night and 43.4% after five, so a ledger that accumulates rarely bounds nothing — and the nightly job's artifact could not become a record by itself, because CI cannot commit. `tools/ci/open_ledger_night_pr.ps1` closes that loop without moving the judgement away from a human: on the scheduled run the same job folds tonight's night onto the branch `ci/stability-ledger` and opens (or updates) the pull request a human merges. The branch is **machine-owned and cumulative**: the script reads the nights already waiting on it at the ref and folds tonight onto their *union*, so a night that is not merged yet is never lost when the next night arrives, and the push is `--force-with-lease`, so the one way this could destroy evidence — a person editing the branch by hand — becomes a refusal instead of a silent overwrite. The commit contains exactly two files (`git show --name-only` is asserted) and is refused outright if the release-claim boundary probe does not exit 0 on the tree it would contain, so the proposal cannot land red; four other refusals guard the checkout it is built on — other modified tracked files, a HEAD that is not the commit the run started from, a review branch that exists remotely but cannot be fetched (rebuilding it would drop the nights on it), and a fold that would lose a night the default branch holds.
- **The step is gated to `schedule` on the default branch, and the gate is load-bearing rather than decorative.** A `GITHUB_TOKEN` push triggers no workflows, so the pull request would otherwise show no checks at all; the script therefore dispatches this same workflow on the branch it just pushed, and that dispatched run **re-enters this job**. If the step could also fold there, every dispatch would fold another night onto the branch and dispatch again — an unbounded chain of writes into the authority record for intermittency. `github.event_name == 'schedule'` on the default branch is what makes that impossible, and the integrity gate asserts the gate, the `-Execute` flag (without it the step would dry-run and report success while pushing nothing) and the job's three write scopes (`contents`, `pull-requests`, `actions`) against the **comment-stripped** workflow — the first version of those checks was satisfied by the header comment that names the same gate and the same scopes, which is a check that can never fail, and it was found by mutating each of the three and requiring the gate to fire.
- **The record is read by Node and never by a shell, and that was a defect found by running it.** The ledger contains non-ASCII characters (the engine note has an em dash); PowerShell decodes a native command's stdout with the console's code page rather than as UTF-8, so a night read through `git show` did not equal the same night on disk. The append-only check refused the fold — which is how it surfaced — but the same decoding would have *written* mangled bytes into the record on the path that restores the branch's ledger. The fix is architectural: the fold tool gained `--into-ref` (append to the ledger as committed at a git ref) and `--require-ref` (refuse unless every night there survives), reads both through `execFileSync` (UTF-8), and the PowerShell script now handles only paths, refs, exit codes and the tool's JSON report. The same run exposed a second Windows trap: PowerShell hands out 8.3 short names (`BADANA~1`) for a long parent while git reports the canonical long path, so a legal path looked like it was outside the repository until both sides were canonicalized.
- **An unattended write into the authority record had to be made safe.** The fold now copies every night already in the record as the exact line it had (only new nights are serialized), writes the result to a staging file, verifies the bytes that actually landed — line count, every pre-existing line still present, every line parseable — and only then renames it over the record. A half-written ledger would not look like a bad write; it would look like a suite regression. The tool's own harness pins this in 16 assertions, including that a refusal leaves the file byte-identical.
- **Scope boundary**: none of this verifies the middleware. It changes whether a green result here can be trusted to mean the same thing twice: repetition observes determinism, the digest pin authenticates the engine, and the engine line makes a degraded environment legible. `--repeat 3` bounds the observation and does not prove determinism — a flake firing one time in ten will usually survive three runs, and the value is in catching the cheap ones, like the race that motivated it. The digest covers the archive, not the extracted binaries, and a cached extraction is trusted as-is (printed). The Unity Editor gate remains the single declared skip: no Editor or Hub exists on this machine, and although the probe is designed for CI (`FEAR_AI_UNITY_REQUIRED=1` turns a skip into a failure), nothing here has run it in a real Editor.

### 34. The Unity EditMode Fixtures Executed Without an Editor (`tools/verification/unity/NUnitTestRunner.cs`, `tools/verification/helpers/editmode_fixtures.mjs`, `verify_dotnet_adapters_compile.mjs` Section C, `verify_unity_editor_tests.mjs`)

Underneath it sat a different one: the five fixtures were **compiled on every run and executed nowhere**, so a test body that could never pass on any machine was held to the standard of "does this compile", and would have been discovered the day someone finally provisioned an Editor — or never. Compiling a test is not running it, and the ledger said so; the fix is to run it.
- **What runs, and the four things that make its green mean something.** `NUnitTestRunner.cs` reflects over the compiled fixtures, runs `[OneTimeSetUp]`/`[SetUp]`/`[Test]`/`[TearDown]`/`[OneTimeTearDown]` in NUnit's order (deliberately including *no `[TearDown]` after a failed `[SetUp]`*, so a teardown on half-built state cannot be reported as a second failure), honours `[Ignore]` with its reason, and writes a machine-readable result. ### 36. The Unity Lifecycle Bodies Are Driven, Not Declared Untestable (`tools/verification/unity/UnityEngineShim.cs` `UnityLifecycle`, `tools/verification/unity/UnityBehaviorHarness.cs`)
- **Five of the adapter's six lifecycle bodies had never been executed by anything.** `FearAIClient` declares `Awake`, `Start`, `OnDestroy` and `FixedUpdate`; the harness invoked `Awake` by reflection and **nothing ever invoked `Start`, `OnEnable`, `Update`, `OnDisable` or `OnDestroy` at all** — `DestroyImmediate` was an empty method. The lifecycle was written down as a limit ("whether Unity calls this when I think it does is an Editor question") and that sentence was true; what it concealed was that nothing *called* them either.
- **The shim now owns the order, and the order is asserted before it is used.** `UnityLifecycle.Wake` runs `Awake` then `OnEnable`; `UnityLifecycle.Frame` runs `Start` **once per component** then `Update`; `Object.DestroyImmediate` runs `OnDisable` then `OnDestroy` on the object and, for a `GameObject`, on every component attached to it. An `async void` body is invoked and not awaited, which means a call proves the synchronous prologue ran, not that its continuations completed. And `FearAgent.cs`/`FearAgentHUD.cs` are still compiled by nothing, so their `Awake`/`Update`/`OnDestroy` remain unexecuted — the new coverage is `FearAIClient`'s, not the package's.
