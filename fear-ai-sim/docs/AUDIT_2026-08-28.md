## 3. Real pathology: migration oscillation

**Finding (500-tick multi-seed audit):** over 500 ticks with attacks every 3rd tick, the closed-world produces **994-998 MIGRATION events** — nearly 2 per tick. The population stays at 1 per town (the loss-gain oscillation cancels within each tick), but the *event log* is dominated by noise.

**Root cause:** the MIGRATION step (2.6.5 in `closed-world.js`) fires when `migrationPressure > 0.5`. Under sustained attacks, the pressure stays above 0.5 indefinitely. The destination is the lowest-population town, but with 2 towns and population 1 each, the destination flips every tick.

**Why this matters:** the event log is not informative. The §7 "Causal Ledger" should record *meaningful* events, not a per-tick oscillation. The current implementation treats the MIGRATION event as "the world is alive" (which is true) but the event log becomes unreadable.

**Fix options:**
1. **Add a per-faction MIGRATION cooldown** — a faction can only emit MIGRATION once per N ticks. This is the same pattern as the raid cooldown (EVID-2026-08-27-RAID-COOLDOWN).
2. **Use a stochastic trigger** — MIGRATION fires with probability `p = sigmoid(pressure - threshold) * 0.1`. This keeps the rate at 0.1 per tick even at high pressure.
3. **Use a "departing" event** — instead of MIGRATION per tick, emit DEPARTURE only when an actual population transfer happens. The 3-town test (EVID-2026-08-28-MIGRATION-IMMIGRATION) already does this; the default 2-town should too.

**Recommended fix:** option 1 (per-faction cooldown). It's the smallest, most consistent change.

## 4. Other findings

### 4.1 Encounter noise

Every tick produces 1 `CANDIDATE_ENCOUNTER` event (200 over 200 ticks). The eligibility check is `evaluateEncounterEligibility`, which likely returns "eligible" for a static catalog. This is a real §532 "Encounter MVP" gap: the catalog has templates but no instantiation.

### 4.2 Market event dominance

`MARKET_TICK` fires 601 times in 200 ticks (about 3 per tick, for 2 towns × 2 goods = 4 per tick, minus suppressive ticks). This is the §155 "Mass balance" contract at work, but the event volume is high. The suppressive mechanism (skip-when-unchanged) helps, but the per-tick produce/consume/spoil step still produces 3 per tick.

### 4.3 Bandit locationAge degeneracy

The bandit's `locationAge` is 200 (it has stayed on `road-b` for the entire 200-tick run). The rest bonus decay (EVID-2026-08-28-REST-BONUS-DECAY) was supposed to let the bandit move occasionally, but the destination-utility model (EVID-2026-08-28-ROAMING-LIVE-WIRE) picked `road-b` and stayed. The `restBonus` for RAID mode is 0, so the bandit has no incentive to leave `road-b`. **This is the PHASE 19 long-horizon degeneracy that was "fixed" but actually still exists** — the bandit is locked in.

### 4.4 No `stance` on the faction

The `faction.stance` is `undefined`. The stance is on the `FactionRelationshipVector` (the pair), not the faction. This is the correct relational design (stance is a property of a pair, not a singleton) but the `summarize` function checks `faction.stance` which is always undefined. A future slice can add a derived `faction.stance` (the stance toward all other factions, aggregated).

## 5. Updated breadth-debt ranking

Per directive §2, the breadth debt is the gap between the current row label and the desired row label. Ranked highest to lowest:

1. **migration** — the oscillation pathology (50/tick of MIGRATION events over 200 ticks = 996 events). **Fix: per-faction cooldown. HIGH.**
2. **encounters** — 20 CANDIDATE_ENCOUNTER but 0 ENCOUNTER. **Fix: instantiation pipeline. HIGH.**
3. **diplomacy** — no treaty system. **Fix: add treaty record + treaty formation event. HIGH.**
4. **factions** — binary `lastDecision` rather than `chooseStance`. **MEDIUM.**
5. **relationships** — single trust per pair, not a→b. **MEDIUM.**
6. **territory** — not modeled. **MEDIUM.**
7. **bandit degeneracy** — `restBonus` for RAID is 0; bandit locks in. **LOW (cosmetic).**

## 6. Recommended next slice

The migration oscillation is the **most impactful** gap because it pollutes the event log. Fix: add a per-faction MIGRATION cooldown (matching the raid cooldown pattern). The closed-world's MIGRATION step should check `if (tick - lastMigrationTick < cooldown) continue;` per faction. The cooldown default: 10 ticks. This reduces the MIGRATION rate from ~2/tick to ~0.2/tick, restoring the event log's signal-to-noise ratio.

After the migration fix, the next slice should be the **encounter instantiation** (Q11). After that, **treaty formation** (Q10).
